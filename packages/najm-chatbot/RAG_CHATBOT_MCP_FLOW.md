# RAG + Chatbot + MCP Flow — Student Management System Example

How the three plugins work together to let an LLM read and manage your data.

---

## TL;DR

You decorate your existing controllers with `@McpTool`. The chatbot picks up a user question, the **tool router** narrows hundreds of tools down to ~10 that are relevant via vector similarity, the **knowledge layer** (RAG over your docs) injects domain context into the system prompt, the LLM proposes tool calls, and any tool marked with `confirm` must be approved before execution. Approved tool calls go through your normal `najm-auth` guards and hit your normal services. No separate "AI backend" exists; the LLM is a client of the same controllers your dashboard already calls.

---

## The three plugins

| Plugin | Job | Without it you'd have to... |
|---|---|---|
| `najm-mcp` | Turns `@Controller` methods into LLM-callable tools, exposes a registry, and carries confirmation metadata. | Hand-write tool definitions + JSON schemas + safety metadata for each method. |
| `najm-rag` (tool router) | Indexes tool names + semantics as vectors; given a user query, returns ~10 relevant tools instead of 200. | Send every tool to the LLM on every turn → blow context, slow, expensive. |
| `najm-rag` (knowledge) | Vector store over your docs (PDFs, FAQ, policies). RAG retrieves passages and injects them into the system prompt. | LLM hallucinates domain rules ("attendance threshold is 80%"). |
| `najm-chatbot` | The agent loop. Coordinates router + knowledge + LLM, manages conversations, streams responses. | Hand-write the streaming/tool-calling/session loop with the AI SDK. |

Your existing app at `C:\Users\pc\Desktop\projects\student management system\dashboard` has:

- `StudentController` — `getStudents`, `createStudent`, `updateGrade`, `getAttendance`, ...

Today admins click buttons. Tomorrow you want them to type:

> *"Send a reminder to parents of students with overdue payments in grade 10A and mark Ahmed Khalil's last absence as excused."*

That's two operations across two domains. With the new stack, here's exactly what happens.

## Setup (consumer side)

### 1. Decorate the methods you want the LLM to use

```ts
// dashboard/src/features/payments/payment.controller.ts
@Controller('/payments')
class PaymentController {
  @Get('/overdue')
  @canRead('payments')
  @McpTool('List payments past their due date, optionally filtered by class')
  @Validate({ query: getOverdueDto })
  async getOverdue(@Query('classId') classId?: string) { ... }

  @Post('/:id/remind')
  @canCreate('notifications')
  @McpTool({
    description: 'Send a payment reminder notification to a payment\'s parent contacts',
    idempotent: true,
    confirm: {
      level: 'notice',
      message: 'payments.confirm.remind'
    }
  })
  async remind(@Params('id') id: string) { ... }
}
```

The same method serves the dashboard UI **and** the LLM. No duplicate code.

Confirmation metadata is declared beside the tool because the module owner knows which actions should pause before execution:

```ts
@McpTool({
  description: 'Mark a student absence as excused',
  idempotent: false,
  confirm: {
    level: 'warning',
    message: 'attendance.confirm.excuseAbsence'
  }
})
async excuseAbsence(@Params('id') id: string) { ... }

@McpTool({
  description: 'Delete a student record',
  destructive: true,
  confirm: {
    level: 'danger',
    message: 'students.confirm.delete'
  }
})
async deleteStudent(@Params('id') id: string) { ... }
```

`confirm: true` means "confirmation required with default text." `confirm: { level, message }` adds a severity and a message. The `message` can be literal text or the same kind of i18n key used by controller responses, so the chatbot can ask in the user's active language.

#### Auto-generated confirmation (safety net)

If a tool is destructive but the developer forgot to add `confirm`, `McpRegistryService.registerTool` fills one in at registration time:

| Signal | Auto-fill |
|---|---|
| `annotations.destructive: true` | `{ level: 'danger', message: 'mcp.confirm.<toolName>', autoGenerated: true }` |
| Tool name matches `delete \| remove \| destroy \| drop \| purge \| wipe \| refund \| revoke` | `{ level: 'warning', message: 'mcp.confirm.<toolName>', autoGenerated: true }` |
| `annotations.destructive: false` (explicit opt-out) | none |
| User-defined `confirm` already present | always wins |

Resolution order: explicit `confirm` → annotation-driven → name-pattern → none.

This means a developer who forgets to mark `deleteUser` will still get a default "Are you sure?" prompt instead of a silent destructive call. The studio surfaces an `autoGenerated: true` flag so admins can see which tools have inferred confirmations and override them with proper localized messages.

### 2. Wire the plugins in `server.ts`

```ts
new Server()
  .use(databaseConfig())
  .use(authConfig())
  .use(mcp({ name: 'sms', version: '1.0.0', path: '/mcp', transports: ['http'] }))
  .use(rag({
    dialect: 'sqlite',
    toolRouting: { enabled: true },   // ← embeds + routes tools
    knowledge: true,                  // ← RAG over docs
    studioApi: true,                  // ← admin UI for managing both
  }))
  .use(chatbot({ conversationStore: 'db' }))
  .load(modulesModule);
```

### 3. Once on boot

- `McpScannerService` walks every `@Controller`, finds `@McpTool` methods, registers them in `McpRegistryService`.
- Confirmation metadata is stored on the registered tool as Najm metadata, separate from MCP SDK `annotations`.
- `ToolIndexerService` embeds each tool's `(name + description + semantics)` into the vector store.
- `KnowledgeService` indexes any docs you've uploaded ("School Policy 2026.pdf", attendance rules, payment terms).

You're done.

## Router internals (how the tool list is actually built)

The router has two non-obvious rules that prevent the LLM from being handed the wrong tool:

### Rule 1 — Primary is picked by aggregate, not `matches[0]`

A naive router takes the top-1 semantic hit as primary. That's fragile: a single noisy phrase that embeds slightly higher than a real cluster wins. Instead the router groups matches by tool, sums each tool's **top-3** similarities, and picks the highest aggregate. Ties (within ε=0.02) break by hit count, then by best single score.

```
matches (top 10):
  products_get_my_products  0.60
  products_delete           0.57   ┐
  products_delete           0.54   │
  products_get_my_products  0.54   │
  products_delete           0.54   │
  products_update           0.54   │ aggregate per tool:
  products_delete           0.53   │   delete:           1.65 (top-3 sum), 6 hits
  products_get_all          0.53   │   get_my_products:  1.65 (top-3 sum), 3 hits   ← loses tiebreak
  products_delete           0.52   │   update:           0.54
  products_get_my_products  0.51   ┘   get_all:          0.53

primary = products_delete  (same aggregate, more hits wins the tiebreak)
```

Top-K is capped at 3 so a tool with 100 phrases doesn't win by sheer count.

### Rule 2 — Write tools never ride along as alternatives

A write tool (`annotations.readOnlyHint !== true`) is included in the final tool list **only if** it is the primary or an explicit dependency. Read-only tools (`readOnlyHint: true`) are free to ride along.

Why: when the user says *"show product 123"*, the router shouldn't also hand the LLM `products_delete` just because its embedding score happens to be similar. The LLM might pick the wrong action; the user's confirmation prompt won't save them if the wrong action is the one that gets confirmed.

```
query: "show product 123"
matches:
  products_get_by_id  0.77   ← primary (read)
  products_delete     0.79   ← higher score, but write & not a dep → DROPPED
  products_get_all    0.71   ← read sibling, kept
```

```
query: "take down listing PRD-884"
matches:
  products_delete     0.83   ← primary (write)
  products_update     0.65   ← write sibling & not a dep → DROPPED
  products_get_by_id  0.50   ← read, kept (useful context for the LLM)
```

The rule is symmetric — there is no "if primary is destructive" special case. A destructive primary still surfaces, with its `confirmation` metadata as the safety net before execution.

### What this replaces

Earlier versions had a "dangerous-intent gate" with `dangerousIntentKeywords` config (e.g., `delete: ['delete', 'remove', 'حذف']`). It tried to use keyword heuristics to decide whether a destructive tool was safe to surface. It was brittle (Darija/French/slang failed), and on miss it silently substituted a different write tool — turning a delete intent into an update. **All of that is gone.** `dangerousIntentKeywords`, `getDangerousCategories`, `hasDangerousIntent`, `applyDangerousGate`, and the `Dangerous Keywords` section in the studio's Settings panel are removed. Safety lives in `tool.confirmation` (auto-filled if missing); routing correctness lives in the alternative-mutation filter.

The preview DTO field that used to be called `gateDecisions` is now `routingDecisions` with shape `{ toolName, kept, reason: 'primary' | 'dependency' | 'read_only' | 'dropped_as_alternative' }` — kept for tests and debugging, no longer surfaced in the default Routing Lab UI.

## Confirmation-first execution

Confirmation is not a replacement for guards. It is a user-consent gate before a tool call mutates important state.

### Where confirmation is declared

Use `confirm` on `@McpTool`:

```ts
@McpTool({
  description: 'Record a payment for a student invoice',
  idempotent: false,
  confirm: {
    level: 'warning',
    message: 'payments.confirm.record'
  }
})
async recordPayment(@Body() dto: RecordPaymentDto) { ... }
```

Recommended levels:

| Level | Use for |
|---|---|
| `notice` | Low-risk writes, notifications, logout. |
| `warning` | Updates, creates, status changes, cart/order edits. |
| `danger` | Deletes, role/permission changes, irreversible or security-sensitive actions. |

### Confirmation flow

```
LLM proposes tool call
  │
  ├─ tool has no confirmation → execute normally
  │
  └─ tool has confirmation
       │
       ├─ validate args with DTO/schema
       ├─ resolve confirmation.message in user language
       ├─ ask user to approve/cancel
       ├─ approved → invoke MCP tool
       └─ cancelled → do not invoke; assistant explains nothing changed
```

Validation should happen before the confirmation prompt. That lets the UI ask a precise question:

```txt
Mark Ahmed Khalil's absence on 2026-05-03 as excused?
```

instead of:

```txt
Run mark_absence?
```

### Language and i18n

`confirm.message` can be a literal message or an i18n key:

```json
{
  "attendance": {
    "confirm": {
      "excuseAbsence": "Mark this absence as excused?"
    }
  }
}
```

The confirmation resolver uses the same language context as normal controller responses. If the active user language is `fr` or `ar`, the prompt should use that locale. If a key is missing, fall back to the raw message, then to a generated default like:

```txt
Confirm running attendance_mark_absence?
```

### Current implementation status

The foundation now exists:

- `@McpTool({ confirm: true })`
- `@McpTool({ confirm: { level, message } })`
- `McpScannerService` carries metadata into `RegisteredTool.confirmation`
- `McpRegistryService.registerTool` auto-fills confirmation for destructive tools (annotation or name pattern) when none is declared, marking it `autoGenerated: true`
- MCP discovery and RAG Studio tool list expose `confirmation`
- RAG Studio shows a `Confirm` badge for tools with confirmation metadata
- RAG Studio can filter the MCP tool table by search, group, and confirmation level

The runtime pause/approve/resume step in the chatbot agent loop is the next layer. Until that is implemented, confirmation metadata is visible (and now exhaustive thanks to auto-fill) but not yet enforced at execution time.

## How RAG works **with** the tool router (the part that confuses people)

There are **two independent vector stores** doing different jobs:

### 1. Tool index (used by the router)

What's indexed: `tool.name + tool.description + tool.semantics`. Each row maps a vector to a tool name.

```
┌────────────────────────────────────────────────────────────┐
│ tool_index_semantics                                       │
│  vector       │ toolName            │ semantics            │
│ ──────────────┼─────────────────────┼──────────────────── │
│ [0.12,0.88…]  │ get_overdue         │ "find late payments" │
│ [0.45,0.21…]  │ remind_payment      │ "send reminder…"     │
│ [0.71,0.04…]  │ mark_absence        │ "excuse an absence"  │
│ [0.33,0.92…]  │ generate_report     │ "create report card" │
└────────────────────────────────────────────────────────────┘
```

**Purpose:** narrow ~200 tools → ~10 relevant tools. The LLM never sees the rest.

### 2. Knowledge index (used by the context provider)

What's indexed: chunks of your docs (school policy PDF, FAQ, internal notes). Each row maps a vector to a passage of text.

```
┌─────────────────────────────────────────────────────────────────┐
│ knowledge_chunks                                                │
│  vector       │ document     │ text                             │
│ ──────────────┼──────────────┼──────────────────────────────── │
│ [0.21,0.55…]  │ policy.pdf   │ "Absences are excused if a       │
│               │              │  doctor's note is uploaded…"     │
│ [0.62,0.18…]  │ payments.md  │ "Late fees apply after 7 days…"  │
└─────────────────────────────────────────────────────────────────┘
```

**Purpose:** ground the LLM in your domain — passed as **context in the system prompt**, not as a tool. No tool call required.

### Why both?

For *"Excuse Ahmed's absence"*:

- **Tool router** finds `mark_absence` (matches the verb).
- **Knowledge layer** retrieves *"Absences are excused if a doctor's note is uploaded"* and injects it. The LLM now knows to ask for the note before calling the tool, instead of silently flipping the flag.

One picks the **actions**, the other shapes the **judgement**. They are complementary, not redundant.

### When to use which

| Question type | Tool router | Knowledge |
|---|---|---|
| *"Show me X"* / *"Do Y"* (action) | ✅ primary | maybe |
| *"What's our policy on Z?"* (knowledge) | unused | ✅ primary |
| *"Why did this happen?"* (mixed) | maybe | ✅ |
| *"Refresh the page"* (UI/no data) | none | none |

Both are opt-in: `rag({ toolRouting: { enabled: true } })` and `rag({ knowledge: true })` are independent flags.

## Auth in this flow (important)

Every tool call goes through your normal `najm-auth` setup. The LLM is **not a bypass**.

```
LLM → McpToolAdapter → PaymentController.getOverdue
                       │
                       └─ @canRead('payments') runs first
                          - reads user from request context
                          - if user lacks the permission → 403
                          - LLM gets "Forbidden" back, retries or apologizes
```

This means a **parent user** chatting can't call admin-only tools even if the LLM tries — the guard rejects it. The router doesn't enforce permissions (it just narrows tools by relevance), but the controller does, and that's the right place for it.

The chatbot itself is mounted at `/api/chatbot/chat` and protected by whatever guards you put on `ChatController` — typically `@isAuth()` so any logged-in user can chat, with their identity flowing into every tool call they trigger.

Confirmation sits before this execution path. The user can still approve a tool they are not allowed to run; the controller guard remains the final authority and returns 403.

## What the new RAG Studio gives you in this picture

The studio is the **admin control plane** for the two vector stores above. From the embedded `<RagStudio />` in your dashboard, an admin can:

- **Knowledge tab** — upload/delete docs, see chunks, re-embed.
- **Routing tab** — view registered tools, filter them by group or confirmation level, inspect confirmation badges/dependencies/parameters, export only the currently visible tools for dependency planning, edit *semantics* (alternative phrasings that bias the router), preview routing for a query, and see what the LLM would have seen.
- **Tests view** — keep routing regression tests in the browser, filter by search/tool/status, run individual tests or all tests, and export only the currently visible rows (for example, failed tests only). A test is marked `low_confidence` when an expected tool's similarity is below the configured `similarityThreshold` — not against a hardcoded value, so lowering the threshold in Settings also relaxes the test bar.
- **Settings tab** — tweak `similarityThreshold`, `maxTools`, `topSemanticHits`, fallback behavior, and dependency JSON. (No `dangerousIntentKeywords` panel anymore — confirmation metadata lives on the tool itself, auto-filled when missing.)
- **Index tab** — inspect embedding/vector-store settings and reindex registered MCP tools.
- **Audit trail** — every write operation through the studio is logged with the admin's user id.

Without the studio, you'd be editing JSON config and running `INSERT` statements to tune the router. With it, the school's IT lead opens the dashboard, drags a PDF in, types a few alternate phrasings for `remind_payment` ("nudge parent", "send late notice"), and the chatbot's accuracy improves immediately.

## Summary in one paragraph

Your existing student-management controllers, decorated with `@McpTool`, become a tool catalog. When a user types a request, the **tool router** uses vector similarity to pick a small relevant subset; the **knowledge layer** retrieves grounding passages from your docs; the chatbot agent assembles `(system prompt + context + tools + history)` and lets the LLM propose a multi-step plan. Tools marked with `confirm` pause for user approval before execution; approved steps are normal calls into your normal controllers, gated by your normal `najm-auth` guards. The new RAG Studio is the admin UI for the vector stores and routing metadata, embedded as `<RagStudio />` inside the same dashboard the rest of your admins already use.
